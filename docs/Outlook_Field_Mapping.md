# ContactDock：旧Outlook CSV項目対応表（設計案）

作成日：2026-10-06。状態：実データ分析済み／保持方法は提案段階。DB・画面・暗号化方式は未決定。

## 目的と対象

旧Outlookの各項目がContactDockでどう扱われるかを追跡する。今回のCSVだけを根拠にしており、PSTの全内容や別のCSVの仕様を保証するものではない。

- 対象：contacts.csv、CP932で厳密にデコード可能、2,342データ行、95列。全行95列。
- 値のある列：51。全件空欄：44。使用件数は空白だけの値を除いて集計。
- SHA-256：`6a0bacf7847f618c7eb884d43cabca1f1f39ac315e54513cb949337ddbe261e9`。
- 個人の氏名・住所・電話・メール・メモ本文は本書へ掲載しない。

## 現時点で確定している方針

ContactDockを今後の連絡先管理に使う。必要な機能・フォルダー・テストのみ必要になった時点で追加する。GitHubとpytestを使い、実連絡先データはGit管理しない。ファイル単位の管理とパスワード保護を要件として扱うが、実現方式は別途検討する。

## 検索・基本操作（採用方針）

メモを最初から通常の検索対象に含める。利用者は旧Outlookのメモを検索に使うために記録していたため、その用途をContactDockでも引き継ぐ。

検索対象は、氏名・フリガナ（氏名と会社名の読み）・会社名・部署・役職・すべての電話番号・メールアドレス・メモとする。通常の検索欄から部分一致で検索し、Enterまたは［検索］で実行する。空白を含む入力は一つの検索文字列として扱う。AND／OR検索は当初実装しない。［クリア］で検索語を消し、全件表示へ戻す。住所を検索対象に含めるかは未決定。

| 操作 | 採用する動作 |
|---|---|
| 詳細表示 | 一覧で選択した連絡先を右側に表示。メモの改行を保持 |
| 新規登録 | ［新規登録］で入力画面を開き、［保存］で登録 |
| 編集 | 選択した連絡先の［編集］で共通の入力画面を開く |
| キャンセル | 入力・変更内容を保存せず閉じる |
| 入力条件 | 姓・名は必須にせず会社名だけでも登録可能。全項目が空の連絡先は保存しない |
| フリガナ | 手入力。自動生成は当初実装しない |
| 削除 | 氏名・会社名を確認画面に表示し、確認後に通常一覧・検索から除外。移行元データは保持 |

削除の復元画面、編集内容の破棄確認、同一連絡先の重複登録時の扱いは未決定。削除の内部方式は後述の案を検討する。

## 検索時の表記の扱い（設計案）

保存・表示する元の値は変更せず、検索語と検索対象の比較用文字列に同じ処理を行う。

| 表記 | 比較時の扱い案 |
|---|---|
| 英字の大文字・小文字 | 区別しない |
| 全角・半角の英数字 | 区別しない |
| 全角・半角カタカナ | 区別しない。濁点・半濁点の有無は区別する |
| 電話番号のハイフン・空白・括弧 | 電話番号の項目内の比較に限り無視する |
| ひらがな・カタカナ | 当初は区別する |

一般の文字列は部分一致で比較する。電話番号は一般の比較に加えて区切り記号を除いた比較を行う。記号を除いた検索語が空になる場合は、電話番号の追加比較を実行しない（記号だけの検索で全電話番号に一致させない）。氏名・会社名・メール・メモの記号や内部の空白は一律に削除しない。電話番号の先頭ゼロは保持し、国番号の補完、内線の推測、ひらがなとカタカナの相互変換は行わない。

検索用の変換方式と無視するハイフン類の範囲は実装前に確定する。過度な変換による意図しない一致を避けるため、匿名の例で確認する。

### 検索の細部（採用方針）

- 検索語の前後の空白だけを除去する。途中の空白は保持し、複数語へ分割しない。
- 前後の空白を除去した結果が空なら、削除されていない連絡先を全件表示する。
- メモは全文を検索対象にする。単一の検索文字列が改行をまたぐ一致は当初扱わず、改行を空白に変換して一致させる処理は行わない。
- 検索結果が0件なら「該当する連絡先はありません」と表示する。前の検索結果の詳細は表示し続けず、選択を解除する。
- 記号だけの入力では、電話番号用の追加比較が全件一致しないようにする。通常の文字列比較では、入力した記号自体の一致を検索する。

## 削除データの保持方法（設計案）

削除対象に削除日時を記録し、通常の一覧・検索・編集対象から除外する方式を提案する。Outlookから取り込んだ連絡先と、ContactDockで新規登録した連絡先の両方に適用する。連絡先本体と関連する電話・メール・住所は内部に保持し、削除時に移行元データも消さない。削除確認をキャンセルした場合は何も変更しない。

初期版では復元画面や完全削除の操作は作らず、必要になった段階で追加する案とする。内部に残ることと、利用者が初期版の画面から復元できることは区別する。

通常の連絡先エクスポートでは削除済みを除外し、管理ファイル全体のバックアップでは含める案とする。移行元CSVの原本再出力には、移行後に削除した連絡先も元の状態で含まれる。削除はデータの消去を意味しないため、操作名と確認文で「一覧・検索から除外し、データは内部に保持する」と明示する。

## 保持方法の提案

1. 日常の閲覧・編集に使う項目と、移行元を確認する元データを分ける。元データは全95列の列名・順序・空欄・値と元行番号を保持する案とする。単なる空欄や既定値も元データからは削除しない。
2. 元CSVのバイト列も同じ管理ファイル内に保存する案とする。これにより文字コード・引用符・改行まで含む原本を再出力できる。解析した値の保持だけではバイト単位の原本復元は保証できない。容量と暗号化方式を検討して確定する。
3. ContactDockで編集した値と移行時の元データは区別する。元データを編集内容で上書きしない。現行データのエクスポートと原本の再出力も用途を区別する。
4. 電話・メールは複数を保持し、元の種類と順序を残す。会社電話1と2を上書き統合しない。メール1〜3を個人用／勤務先用へ推測分類しない。
5. 住所は会社・自宅・その他を分け、国／地域・郵便番号・都道府県・市町村・番地・私書箱を保持する。結合住所は表示用に生成し、分解した原情報を残す。
6. 電話番号・郵便番号は文字列で保持する。元値を書き換えず、必要な検索用正規化値を別に生成する。メモの改行も保持する。
7. 未使用項目は今回の通常画面に追加しない案とする。将来のCSVに値が現れた場合は元データへ保持し、未対応項目として知らせる。黙って捨てない。

## 最小DB構造（設計案、2026-10-06）

SQLCipherによる一つの暗号化DBに、次の5テーブルを設ける案とする。本節は実装前の設計案であり、DBファイルや本体コードはまだ作成しない。移行元CSV原本のDB内保持も、この案で具体化する。

| テーブル | 役割 |
|---|---|
| contacts | 氏名・読み・所属・メモなど、連絡先本体と削除日時、移行時の元行情報 |
| contact_phones | 連絡先に属する複数の電話・FAX・無線電話・テレックス |
| contact_emails | 連絡先に属する複数のメールと表示名・種類 |
| contact_addresses | 会社・自宅・その他の住所と構成要素 |
| import_batches | CSV取込単位の情報、ヘッダーと元CSVのバイト列 |

### contacts

- id：連絡先の内部ID。氏名・メールをIDや一意条件にはしない。
- family_name / given_name / family_name_kana / given_name_kana：姓・名とそれぞれの読み。
- company_name / company_name_kana / department / job_title：会社名・読み・部署・役職。会社マスターは作らない。
- note / web_page / birthday：メモ、Webページ、誕生日。誕生日は文字列で保持する。日付書式と不正値の扱いはインポーター設計で決める。
- created_at / updated_at / deleted_at：作成・更新・削除日時。deleted_atがNULLの連絡先を通常一覧と検索対象にする。
- import_batch_id / source_record_number / source_values_json：移行時の取込単位、CSVのデータレコード番号、全95列の解析前の値を文字列配列で保存するJSON。JSONの値はCSVパーサーで取り出した後、正規化する前の値。CSVの引用符や改行コードを含むバイト列の原本はimport_batchesに保存する。

元データの列名・順序は取込単位のヘッダーと対応付ける。配列で保持することで、同名ヘッダーが現れた場合も辞書化による上書きを避ける。source_record_numberはヘッダーを除く1始まりのレコード番号であり、物理行番号ではない。

Outlookから取り込む場合は移行元3項目をセットで設定し、ContactDockで新規登録した場合はすべてNULLにする。移行後に編集しても移行元情報は変更しない。取込単位と元レコード番号の組合せは重複不可とする案。同じCSVの再取込の扱いは後述の採用方針に従う。

### contact_phones

id / contact_id / kind / position / valueを持つ。kindは会社電話・会社FAX・携帯電話・自宅電話・会社代表電話・その他電話・その他FAX・無線電話・テレックス等を区別する。会社電話1と2は同じkindの異なるpositionに対応し、表示時に元の順序を再現する。valueは文字列で、先頭ゼロや元の記号を保持する。元のOutlook列名はヘッダーと元値からも追跡できる。

### contact_emails

id / contact_id / position / address / display_name / source_typeを持つ。positionはOutlookのメール1〜3を維持し、空のメール1を飛ばしてメール2をメール1へ詰めない。表示名や種類だけに値がある入力も捨てず保持できるよう、アドレス必須の制約はインポート仕様を確認してから判断する。個人用・勤務先用へ推測分類しない。

### contact_addresses

id / contact_id / kind / country_region / postal_code / prefecture / city / street / post_office_boxを持つ。kindは会社・自宅・その他で、各連絡先・区分につき1件とする。postal_codeを含め値は文字列で保持する。住所の一部だけがある場合も保存する。今回未使用の住所2・住所3は通常項目として追加せず、元データへ保持する。

### import_batches

id / imported_at / source_filename / source_encoding / source_sha256 / record_count / headers_json / original_csvを持つ。original_csvはBLOBとして、元CSVのバイト列を暗号化DB内に保存する。source_filenameはファイル名のみとし、利用者のPC上の絶対パスは保存しない。record_countは元CSVのデータレコード数とし、部分取込は初期案では行わない。

ヘッダー・全行を検証した後、取込単位と全連絡先・関連項目を一つのトランザクションで保存する案。失敗した場合は取込単位も含めロールバックする。複数の独立した履歴テーブルや取込失敗ログのDB保存機能は当初作らない。

### 共通規則と検証

- 子テーブルと取込単位の参照は外部キーでつなぎ、各接続で外部キー検証を有効にする。
- 通常の削除はcontactsのdeleted_atのみ変更し、子テーブルと元データは残す。通常検索とエクスポートは削除済みを除外する。
- スキーマ版数はDB内のuser_version等で管理する案。具体的な版数と移行処理は最初の実装時に決める。
- 初期版は通常の部分一致検索から始める。FTS用テーブル、検索正規化値の永続保存、タグ、会社マスター、変更履歴テーブルは必要が判明するまで追加しない。
- 通常のデータ空欄は空文字、削除前のdeleted_atや新規登録時の移行元参照なしはNULLとする案。日時はUTCの一定形式で保存し、表示時にローカル時刻へ変換する。
- メールや電話の重複を一意制約で排除しない。共有電話や共有メール、同姓同名を許容する。
- 親子関係、順序、部分住所、元値と原本の保持、取込失敗の全体ロールバックをpytestで確認する。

DB設計として残る判断は、電話の種類とpositionの厳密な対応、日付の書式、全項目空の判定、索引、通常エクスポートの書式である。検索時の正規化方式と配布ライセンスも未確定。

## CSV再取込の扱い（採用方針、2026-10-06）

- 元CSVのバイト列のSHA-256を、同じ管理DB内の取込済みimport_batches.source_sha256と照合する。
- 同一ハッシュのCSVは再取込しない。ファイル名や保存場所を変更しても同一CSVとして検出する。取込済みである旨を表示し、既存連絡先・取込単位は変更しない。
- 同一CSVから取り込んだ連絡先を削除済みにしていても、同一CSVの再取込では復元・追加しない。
- バイト列が変わったCSVは別の入力として扱う。文字コード・改行コードだけの違いもハッシュが変わるため、内容が同じかもしれないCSVを完全には検出できない。
- 変更されたCSVを取り込んでも、既存連絡先の更新・統合は自動では行わない。新しい取込単位として新規連絡先を追加する。
- 取込前に、追加件数と「既存連絡先は更新せず追加します。以前のCSVを変更したものの場合、連絡先が重複する可能性があります。」という説明を表示し、利用者の実行操作後に保存する。キャンセル時は変更しない。
- 失敗してロールバックした取込単位は取込済みとしない。修正後の再実行を可能にする。

同一CSVの保存をDB側でも防ぐため、source_sha256に一意制約を設ける案とする。意味上の重複判定、比較・更新取込、重複統合は必要になった段階で検討する。

実装時には、初回取込・同一ファイルの再取込・改名後の再取込・削除後の再取込拒否・変更CSVの新規追加・取込キャンセル・取込失敗後の再実行を匿名データで検証する。

## CSVからDBへの変換規則（設計案、2026-10-06）

元値と元CSVは常に保存し、通常項目へ移す際も文字列の前後空白や改行を無断で削除しない。空欄判定にtrimを使っても、非空値の保存には元の文字列を使う。

### 電話項目の対応

positionは種類内の1始まりの順序とする。

| Outlook列 | kind | position |
|---|---|---:|
| 会社電話 | work_phone | 1 |
| 会社電話 2 | work_phone | 2 |
| 会社代表電話 | company_main_phone | 1 |
| 会社 FAX | work_fax | 1 |
| 自宅電話 | home_phone | 1 |
| 自宅電話 2 | home_phone | 2 |
| 携帯電話 | mobile_phone | 1 |
| その他の電話 | other_phone | 1 |
| その他の FAX | other_fax | 1 |
| 無線電話 | radio_phone | 1 |
| テレックス | telex | 1 |

(kind, position)はcontact_idごとに一意とする案。番号自体は一意にしない。空欄なら子レコードを作らず、会社電話2だけがある場合もposition=2を維持する。FAX・テレックスも種類を保った電話等として検索対象に含める。

### メール・住所の保存条件

メールは同じ番号のアドレス・表示名・種類のいずれかに非空値があれば保存し、positionは1〜3を維持する。メールの形式が想定外でも元値を消さず、取込時に警告できるようにする。メールアドレスの大文字小文字を保存時に変更しない。

住所は同じ区分の通常項目のどれか一つに非空値があれば保存する。私書箱だけの住所も対象とする。区分の構成要素を連結して保存する方式は採らない。

### 誕生日

今回のCSVでは実日付1件はYYYY/M/D形式だった（個人の日付は文書に掲載しない）。空欄と00/0/0は通常項目上の未設定として扱い、元値には残す。実在する日付と確認できるYYYY/M/DまたはYYYY-MM-DDは通常項目でYYYY-MM-DDに統一する案。それ以外や存在しない日付は推測変換せず、文字列のまま保持して警告する。月日順の推測や年の補完は行わない。

### 空の連絡先・行の扱い

新規登録時は、氏名・所属・メモ・Webページ・誕生日・電話等・メール・住所に一つでも非空値があれば保存できる案とする。内部ID・日時・移行元情報だけでは入力済みと判定しない。

CSV取込では、全項目空白のレコードは不正入力として対象のデータレコード番号を報告し、取込全体を止める案。今回のCSVにこの種のレコードは0件だった。通常項目に値がなくても、元項目に情報がある連絡先は黙って削除しない。未対応項目だけに値がある場合は、取込前に知らせ、元データを保持した連絡先として取り込む案とする。

### 構造と文字コードの検証

CP932を今回の入力形式として対応する。UTF-8 BOM付き・UTF-8等の追加対応は必要に応じて決める。復号エラーを置換文字で隠さない。各レコードの列数がヘッダーと一致しない場合、CSVの引用構造が不正な場合、ヘッダーが重複して通常項目を一意に対応できない場合は保存前に停止する。ヘッダーの未知列と、その非空値の件数は取込前に知らせる。列順だけの変更はヘッダー名で対応し、元の列順も保存する。

初期の正式インポーターは今回の95列のOutlook CSVを対象にする案。必須ヘッダーの不足を許容する範囲は実装前に確定する。警告は不正構造による停止と区別し、元情報を保持した上での取込可否を画面で確認できるようにする。

検証には、会社電話2のみ、第3メールのみ、表示名のみ、郵便番号のみ、私書箱のみ、改行入りメモ、未設定日付・不正日付、空レコード、列数不一致、重複ヘッダー、未知列の非空値を含む匿名fixtureを使う。

## CSV読取・変換の初期実装（2026-10-06）

Linux／Python 3.12で既存9件と新規16件、計25件成功。利用者の実CSVを読み取り専用で確認した結果は2,342件、95列、電話等5,075項目、メール2,122項目、住所2,202項目。全行の元95値を保持し、raw_only_field警告は3件。実CSV・個人の値はソース・テストへ含めていない。Windowsで今回追加分の確認はこれから実施する。

CSV読取の結果はメモリ上のプレビューであり、同一CSVの再取込検出、取込確認画面、DBへの一括保存はまだ未実装。
